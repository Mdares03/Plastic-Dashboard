## 1. Task A — "Set up pairing later" for machines

### Why

The onboarding wizard (`app/(app)/onboarding/page.tsx`) provisions machines via
`lib/onboarding/provision.ts`, which generates each new machine a pairing code with a
**24-hour expiry** (provision.ts:124–125). But:

- the wizard **never displays** those codes — `/api/onboarding/import` returns only `counts`
  (see `app/api/onboarding/import/route.ts`), so the codes silently expire unseen;
- there is **no endpoint to (re)issue a pairing code** for an existing machine — the only code
  generation paths are machine creation (`POST /api/machines`, route.ts:150) and wizard provisioning.

So today, if you don't pair within 24h of creation, the machine can never be paired. The goal:
add machines now, pair each edge reader whenever it's physically ready.

### Current pairing mechanics (do not change the edge contract)

- `Machine` fields: `pairingCode` (unique), `pairingCodeExpiresAt`, `pairingCodeUsedAt`, `apiKey`
  (prisma/schema.prisma:115–149). **`apiKey` presence does NOT mean paired** — provisioning
  pre-creates it. *Paired* = `pairingCodeUsedAt != null` (the pair endpoint stamps it).
- Edge calls `POST /api/machines/pair` with the 8-char code (IP rate-limited, single-use,
  expiry-gated) and receives `{cloudBaseUrl, machineId, apiKey}` — `app/api/machines/pair/route.ts`.
  Re-pairing reuses the existing `apiKey` if present (line 55–58), so re-issuing a code for an
  already-paired machine is non-destructive.
- Code generation: `generatePairingCode()` in `lib/pairingCode.ts`; uniqueness-checked variant
  `freshPairingCode(tx)` in `lib/onboarding/provision.ts:43`.

### Build

1. **New endpoint `POST /api/machines/[machineId]/pairing-code`** (add to the existing
   `app/api/machines/[machineId]/route.ts` file's folder as a sibling route):
   - Session-auth via `requireSession()`, role OWNER or ADMIN (mirror the role checks used in
     `app/api/machines/route.ts` POST).
   - Verify the machine belongs to `session.orgId`.
   - Generate a fresh unique code (reuse/extract the `freshPairingCode` uniqueness loop — move it
     into `lib/pairingCode.ts` so provision.ts and this route share one implementation), set
     `pairingCodeExpiresAt = now + 24h`, clear nothing else. Do NOT touch `apiKey` or
     `pairingCodeUsedAt` (history of "was paired before" stays intact; the pair route re-stamps it).
   - Return `{ ok, pairingCode, pairingCodeExpiresAt, paired: pairingCodeUsedAt != null }`.
   - Write a `SettingsAudit` row (source `"pairing-code:regenerate"`) like other config mutations.
2. **Machines page (`app/(app)/machines/MachinesClient.tsx`):**
   - Each machine row/card gets a pairing status pill: *Emparejada* (`pairingCodeUsedAt` set),
     *Código activo* (unpaired, unexpired code exists — show remaining time), *Sin emparejar*
     (no code or expired). The list API (`GET /api/machines`) must expose `pairingCodeUsedAt`
     and `pairingCodeExpiresAt` (+ the code itself only for OWNER/ADMIN) — check what it returns
     today and extend the select.
   - "Generar código de emparejamiento" button (OWNER/ADMIN) → calls the new endpoint → opens the
     **existing** pairing modal (MachinesClient.tsx ~439–470, strings `machines.pairing.*`) with
     the fresh code. Reuse that modal; don't build a second one.
3. **Wizard (`app/(app)/onboarding/page.tsx` + `app/api/onboarding/import/route.ts` +
   `lib/onboarding/provision.ts`):**
   - Make `provisionOrgSetup` return, per created machine, `{name, id, pairingCode, pairingCodeExpiresAt}`
     (it already knows them); pass through the import route into the wizard's `result`.
   - On success, the review step shows a "Emparejamiento" panel: each machine with its code +
     expiry, copy buttons, and an explicit escape hatch: *"¿Los lectores aún no están instalados?
     Puedes emparejar después desde Máquinas → Generar código"* linking `/machines`.
   - Only machines **created** by this import get codes; machines that already existed (upsert path)
     show their pairing status instead.
4. **i18n:** add the new keys to BOTH `lib/i18n/es-MX.json` and `lib/i18n/en.json` (es-MX is the
   client-facing source of truth; keep the existing `machines.pairing.*` naming family).
5. **Tests** (`tests/`, vitest, no DB — follow the existing pure-function style):
   - unique-code retry loop extracted to `lib/pairingCode.ts` gets a unit test (collision then success);
   - route-level: MEMBER → 403, cross-org machine → 404, regenerate resets expiry (if there's no
     existing route-test harness, cover the extracted pure parts and note the manual check).
6. **Manual verification:** create a machine → let the code expire (or null it in dev DB) →
   regenerate → pair with `curl -X POST /api/machines/pair -d '{"code":"..."}'` → confirm
   `pairingCodeUsedAt` set and heartbeats accepted.

## 2. Task B — Show "Ahorros por causa" under placeholder rates (with a visible note)

### Why

Financial rates currently default to the documented `1/min` stub (1,1,1,1,1 —
see `docs/ROI_MODEL.md`). `resolveCostPerMin` (`lib/financial/costPerMin.ts`) returns
`placeholder: true` when the machine rate is null or `<= 1`. Today the Downtime page **hides**
the money story while placeholder:

- `components/downtime/DowntimePageClient.tsx:1066` — `estCost` KPI is `null` under placeholder;
- `:1073–1086` — `savingsByReason` returns `[]` under placeholder;
- `:1094` — `showMoneyCol` false → money column hidden in tables;
- `:1667–1673` — the "Ahorros por causa" card renders a "configure rates" note instead of the table.

The ROI page already does what we want: it **shows the numbers** and stacks a warning
(`app/(app)/reports/roi/page.tsx:236`, string `roi.savings.placeholder`). Make the Downtime page
consistent with that pattern.

### Build

1. In `DowntimePageClient.tsx`, compute and render the money story **whenever
   `costRate.costPerMin > 0`**, placeholder or not:
   - `savingsByReason`: drop the `costRate.placeholder` early-return (keep the `!costRate` guard);
   - `estCost` and `showMoneyCol`: same treatment — money renders, flag only drives the note;
   - "Ahorros por causa" card: always show the table when there are rows; when
     `costRate.placeholder` is true, render an amber/warning banner **above the table** (reuse the
     visual style of the ROI page's warning) with the new copy below, keeping the existing
     `/settings` link ("Configurar tarifas →"). The green "Total recuperable" chip can render in a
     neutral tone under placeholder so illustrative money doesn't read as confirmed money.
2. **The note must disappear by itself** once real rates exist — that's already how the flag works:
   `placeholder = !profile || machineCostPerMin == null || machineCostPerMin <= 1`. No new state,
   no dismissal logic. Document the known quirk: a *genuine* rate of exactly 1/min would still read
   as placeholder (accepted; noted in `docs/ROI_MODEL.md`).
3. **i18n** — replace/add (es-MX authoritative, mirror in en.json):
   - `downtime.savings.placeholderNote`: `"⚠️ Tarifas de relleno (1/min): los minutos de paro son reales, pero las cifras en dinero son ilustrativas. Captura tus tarifas reales en Configuración → Finanzas para ver ahorros verdaderos."`
   - Keep `downtime.savings.placeholder` only if still referenced; otherwise remove the dead key
     from both locale files.
4. **Congruence rule (R5/#13):** the per-reason money must remain `minutes × costPerMin` over the
   SAME minute rows the page already shows (`computeMetricRows(baseRows, "minutes")`) — rows must
   sum to the Est. cost KPI by construction. Do not introduce a second money source.
5. **Tests:** the savings-by-reason mapping is inline in the component today. Extract the pure part
   (rows + rate → savings rows + total) into e.g. `lib/analytics/savingsByReason.ts`, unit-test it
   (placeholder rate still yields rows; total = Σ; zero-cost rows filtered), and have the component
   import it.
6. **Check the other placeholder-gated surfaces for consistency** (`grep -rn "placeholder" app components | grep -i cost`):
   Downtime page money column + heatmap money, weekly report money, financial page. Decision:
   *show money + note everywhere* (the ROI-page pattern). One page hiding money while another shows
   it is exactly the "numbers waver" impression we're eliminating.

## 4. Context for judgment calls

The client paused the project asking for: robustness/clarity of data → reports, translating data
into concrete actions, and a defensible ROI. These two tasks serve that directly: pairing-later
removes the biggest onboarding footgun (dead codes = machines that never report = holes in the
data), and showing "Ahorros por causa" from day one — clearly labeled illustrative — teaches the
money story before finance config happens, while the note's disappearance rewards configuring real
rates. When in doubt, choose the option that keeps every screen's numbers reconcilable with every
other screen's.
